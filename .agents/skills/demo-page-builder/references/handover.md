# 交付确认：打 Git Tag 与生成交接文档

用户在浏览器里确认页面效果满意之后（"可以了"、"就这样"、"满意"、"没问题"等明确认可），必须执行本流程：打 git tag 标记本次交付，并生成与 tag 同名的交接文档。

## 触发条件

- 仅当用户**明确认可**本次页面/改动时执行，一轮会话可能产出多个 tag（每次认可一次）
- 用户只是没回复、说"再看看"或提出新修改意见时，**不执行**，继续按交付循环改到认可为止
- 执行前先完成该改动的 git 提交与推送（见 SKILL.md 的 Git 提交节），保证 tag 打在包含全部改动的最新提交上

## Tag 命名

格式：`deliver-<语义名>-<YYYYMMDD>-<两位序号>`

- **语义名由 AI 从本次交付内容中分析提炼**：用**中文**短语概括本次交付的页面/功能，要让人仅凭 tag 名就能看懂这次交付了什么（如 `用户管理页`、`仪表盘图表`、`登录页`）；禁止 `新页面`、`修改`、`更新` 这类无信息量的名字
- **后缀** = 当天日期 + 两位序号，用于区分同主题的多轮交付：日期取当天，序号从 `01` 开始；先用 `git tag -l 'deliver-*'` 查已有 tag 决定序号
- 示例：`deliver-用户管理页-20260807-01`、`deliver-仪表盘图表-20260807-02`
- 执行 `git tag <tag名>` 后连同提交一起 `git push origin <tag名>` 推送到远端
- 语义名**只用中文加日期数字后缀**：不含空格、英文和特殊符号，保证 git 与文件名跨平台可用（git 原生支持 UTF-8 tag 名，交接文档文件名与 tag 同名，同样是中文）

## 交接文档

- 路径：`docs/handover/<tag名>.md`，**文件名必须与 tag 名完全一致**（如 tag 为 `deliver-用户管理页-20260807-01`，文档就是 `docs/handover/deliver-用户管理页-20260807-01.md`）
- 本 skill 的使用者是**产品经理**，生成网页 demo 的目的是给其他人演示/试用。交接文档的**新增页面**与**复刻 demo** 两种场景要求完全一致。交接文档内容**只写五部分**：
  1. **使用说明**——描述**使用者实际使用这个页面的操作逻辑**：在这个网页上可以做什么、按什么顺序点哪里、每一步会发生什么、最终能完成什么事，并配一张对应的**用户操作流程图**（用 Mermaid `flowchart` 描述从进入页面到完成目标的全过程与分支，让演示者照着流程就能讲、照着流程就能试；**Mermaid 生成按 `references/mermaid.md` 执行**）；**写使用说明前，凡是有不明确、含糊或缺失信息的地方（页面能做什么、操作路径、边界/异常、给谁用等），必须向产品经理反问澄清，得到明确结论后方可继续撰写**——不得自行假设或脑补页面行为，问清前不写这部分内容；
  2. **DOM 树与组件说明**——给出页面的 DOM 树结构（用缩进/树状列出页面各区块的嵌套层级），并在树上标注每个节点对应的**当前项目自身的组件**（即本项目 `src/components`、`src/pages` 下实际存在的组件，而非 antd 等组件库里的原子组件），以及它们由哪些**白名单原子组件**（antd / Ant Design Pro / Ant Design X 等清单内组件）组合而成；说明每个当前项目组件归属哪个区块、承担什么职责，让拿到 demo 的人一眼看懂页面由项目自身的哪些组件构成、各自怎么由原子组件拼出来；
  3. **设计与用户体验（Design & UX）**——交代本页面的设计依据与全局状态表现，让拿到 demo 的人明白这套页面为什么这么设计、各状态怎么呈现。必须包含：
     - **设计原则 / UX 原则**：列出指导本页面的设计原则（如「操作路径最短」「关键操作可撤销」「状态反馈明确」），有公司/团队 Design System 时给出链接
     - **用户流程（User Flow）**：主流程（Happy Path）用文字或 Mermaid 描述「开始 → 步骤 → 决策点 → 结束」，并列关键分支路径与异常/退出路径（Mermaid 生成按 `references/mermaid.md` 执行）
     - **原型与设计稿**：交互原型（Figma/Axure 等）与视觉设计稿（UI）链接，并用表格列出关键页面清单（页面名称 / 说明 / 设计稿链接或截图）
     - **关键交互说明**：导航方式、手势/操作约定（移动端点击/长按/滑动）、动画与反馈要求（如需）
     - **全局状态与边界处理**：用表格列出各状态类型（加载中 / 空状态 / 错误状态 / 无权限 / 网络异常等）的**表现要求**（如加载中显示 Skeleton / 转圈 / 按钮 loading 态，空状态给文案 + 引导操作按钮，错误状态给明确错误原因 + 重试/返回入口等）
  4. **功能说明（按功能逐条写）**——对页面里的每个功能，**当作一个用例**来写，让拿到 demo 的人照着就能理解每个功能的目标、操作与校验规则。每个功能按下面的用例结构逐项说明（沿用 `use-cases.md` 的用例方法论，此处已并入模板）：
     0. **用例概述**（用表格或字段列出）：用例名称、用例编号（统一前缀如 `UC-LOGIN-01`，按模块分组）、参与者（游客/已登录用户/管理员等）、优先级（P0/P1/P2，P0 为核心）、前置条件（用例开始前必须满足的状态）、后置条件（成功结束后系统达到的状态）、触发事件（用户或系统触发本用例的动作）
     1. **功能目标**：用户能完成什么、解决什么问题（对应用例概述的「用例名称」）
     2. **用户场景 / 用户故事**：作为 [角色]，我希望 [动作]，以便 [价值]（对应「参与者」）
     3. **页面/界面说明**：入口（从哪里进入）、布局说明（顶部 / 主体 / 底部操作区，可配截图或原型链接）
     4. **正常流程（交互与操作流程）**：按步骤列出「点 X → 弹出/跳转 → 填写 → 提交 → …」，每步动作 + 系统反馈，按用户真实操作顺序（聚焦 → 输入 → 校验 → 提交 → 结果）
     5. **业务规则（字段规则）**：用表格列出每个字段（字段名 / 类型 / 是否必填 / 校验规则 / 默认值 / 错误提示文案 / 备注），并把可测试的硬性规则（敏感词脱敏、防重复发布、防暴力破解、长度/格式限制等）一并列出；涉及产品决策但未确认的（如失败锁定策略）如实标注「需产品确认」，不擅自假定
     6. **各种状态表现**：正常态 / 加载态（按钮 loading、不可重复点击）/ 成功态（Toast「操作成功」+ 刷新或跳转）/ 失败态（提示原因 + 保留已填内容）/ 空态 / 权限不足
     7. **异常流程（异常与边界场景）**：表格化列出每条异常（编号 / 触发操作 / 系统表现 / 处理结果），穷举输入校验、格式校验、长度限制、网络异常、重复提交、权限不足等场景；编号与正常流程区分（如 A1–A9 / B1–B7）
     8. **验收标准（可测试）**：用 `[ ]` 勾选项列出可测的验收标准（如「用户按主流程可顺利完成操作」「所有错误提示文案正确且位置合理」「加载/空/错误状态均有明确反馈」「移动端与桌面端表现符合设计稿」）
     > 写作参考：完整示例见 `use-cases.md` 的登录/评论用例，以及本目录下的 `handover.example.md`。**正常流程分步编号、异常流程表格化、业务规则可测试**是三条硬性要求。
  5. **对话过程摘要**——按时间顺序概括产品经理的原始需求、迭代中的每轮反馈与修改（改了什么、为什么改），直到确认满意，**放在文档最后**；
  除此之外不写交付概述、最终状态、如何继续等其他内容
- **写作参考**：拿不准格式时，照本目录下的 `handover.example.md` 示例写——尤其 **DOM 树部分，树的每一棵子树必须终止于白名单原子组件**（antd / @ant-design/pro-components / @ant-design/x / @ant-design/icons 等清单内组件），项目自身组件（`src/components`、`src/pages` 下的组件）只负责组合这些原子组件、承载业务逻辑，**不能成为 DOM 树的叶子**；在 DOM 树上把每个当前项目组件标注出来，并说明它由哪些白名单原子组件拼成，让拿到 demo 的人一眼看懂
- 交接文档写完后再执行一次 `git add -A && git commit && git push`，提交信息用 `docs: <tag名> 交接文档`，**确保 tag 指向的提交与文档提交相邻**——若 tag 已先于文档提交打上，需删除本地和远端 tag 后重打（`git tag -d <tag>` + `git push origin :refs/tags/<tag>`），或在一开始就先写文档再打 tag（推荐顺序：**写文档 → 提交推送 → 打 tag → 推 tag**）

## 推荐执行顺序

1. 用户确认满意
2. 业务改动的提交与推送（若还没提交）
3. 写 `docs/handover/<tag名>.md`，提交并推送（`docs: <tag名> 交接文档`）
4. `git tag <tag名>` 并 `git push origin <tag名>`
5. 告知用户：tag 名、交接文档路径
