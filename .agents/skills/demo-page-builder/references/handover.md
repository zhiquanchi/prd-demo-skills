# 交付确认：打 Git Tag 与生成交接文档

用户在浏览器里确认页面效果满意之后（"可以了"、"就这样"、"满意"、"没问题"等明确认可），必须执行本流程：打 git tag 标记本次交付，并生成与 tag 同名的交接文档。

## 触发条件

- 仅当用户**明确认可**本次页面/改动时执行，一轮会话可能产出多个 tag（每次认可一次）
- 用户只是没回复、说"再看看"或提出新修改意见时，**不执行**，继续按交付循环改到认可为止
- 执行前先完成该改动的 git 提交与推送（见 SKILL.md 的 Git 提交节），保证 tag 打在包含全部改动的最新提交上

## Tag 命名

格式：`deliver-<语义名>-<YYYYMMDD>-<两位序号>`

- **语义名由 AI 从本次交付内容中分析提炼**：用**中文**短语概括本次交付的页面/功能，要让人仅凭 tag 名就能看懂这次交付了什么（如 `用户管理页`、`仪表盘图表`、`登录页`）；禁止 `新页面`、`修改`、`更新` 这类无信息量的名字
- **后缀** = 当天日期 + 两位序号，用于区分同主题的多轮交付：日期取当天，序号从 `01` 开始；先用 `git tag -l 'deliver-*'` 查已有 tag 决定序号
- 示例：`deliver-用户管理页-20260807-01`、`deliver-仪表盘图表-20260807-02`
- 执行 `git tag <tag名>` 后连同提交一起 `git push origin <tag名>` 推送到远端
- 语义名**只用中文加日期数字后缀**：不含空格、英文和特殊符号，保证 git 与文件名跨平台可用（git 原生支持 UTF-8 tag 名，交接文档文件名与 tag 同名，同样是中文）

## 交接文档

- 路径：`docs/handover/<tag名>.md`，**文件名必须与 tag 名完全一致**（如 tag 为 `deliver-用户管理页-20260807-01`，文档就是 `docs/handover/deliver-用户管理页-20260807-01.md`）
- 内容**只写两部分**：1）用户对页面的操作描述——用户在这个页面（或多个页面）上做了什么操作、提出了什么操作要求，如实记录；2）**对话过程摘要**——按时间顺序概括用户的原始需求、迭代中的每轮反馈与修改（改了什么、为什么改），直到用户确认满意，**放在文档最后**；除此之外不写交付概述、最终状态、如何继续等其他内容
- 交接文档写完后再执行一次 `git add -A && git commit && git push`，提交信息用 `docs: <tag名> 交接文档`，**确保 tag 指向的提交与文档提交相邻**——若 tag 已先于文档提交打上，需删除本地和远端 tag 后重打（`git tag -d <tag>` + `git push origin :refs/tags/<tag>`），或在一开始就先写文档再打 tag（推荐顺序：**写文档 → 提交推送 → 打 tag → 推 tag**）

## 推荐执行顺序

1. 用户确认满意
2. 业务改动的提交与推送（若还没提交）
3. 写 `docs/handover/<tag名>.md`，提交并推送（`docs: <tag名> 交接文档`）
4. `git tag <tag名>` 并 `git push origin <tag名>`
5. 告知用户：tag 名、交接文档路径
