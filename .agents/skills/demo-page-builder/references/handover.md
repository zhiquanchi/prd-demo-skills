# 交付确认：打 Git Tag 与生成交接文档

用户在浏览器里确认页面效果满意之后（"可以了"、"就这样"、"满意"、"没问题"等明确认可），必须执行本流程：打 git tag 标记本次交付，并生成与 tag 同名的交接文档。

> **硬性闭环**：生成交接文档不是自由发挥，而是**先套固定模板、生成后跑机器校验**。动手前必须先读 `references/handover.template.md`（固定模板，逐字照抄只换占位符）、`references/handover.md`（本细则）、`references/mermaid.md`（Mermaid 语法）三份文件；生成后必须运行 `node scripts/validate-handover.mjs docs/handover/<tag名>.md` 自检，**任一检查项不通过不得向用户报告完成**（完整闭环见 `SKILL.md` 的「交接文档生成（硬性闭环，先模板后校验）」一节）。

## 触发条件

- 仅当用户**明确认可**本次页面/改动时执行，一轮会话可能产出多个 tag（每次认可一次）
- 一轮认可覆盖**多个页面**（新增或修改了多个主页面）时，**按页面拆分：每个页面一个 tag + 一份同名交接文档**，禁止把多个页面塞进同一份文档（细则见下方「多页面交付：按页面拆分」）
- 用户只是没回复、说"再看看"或提出新修改意见时，**不执行**，继续按交付循环改到认可为止
- 执行前先完成该改动的 git 提交与推送（见 SKILL.md 的 Git 提交节），保证 tag 打在包含全部改动的最新提交上
- 生成任何文档前先执行下方「存量核对与补全」：在 git 中确认对应文档是否已存在，缺失的并入本次补全

## 已交付页面的后续修改（交付修订，强制）

页面已有 `deliver-*` tag 后，任何影响其可见结果或可操作行为的改动，包含布局、样式、公共导航/壳层、页面业务代码、交互和 mock 数据契约，均是新的交付修订。不能只提交代码而不让交接文档跟随最新页面。

**修改后不创建新交接文档，在原交接文档上就地更新。**

1. **修改前定位基线**：用 `git log --oneline --all -- <页面路径> <相关公共组件路径>`、`git tag -l 'deliver-*'` 找到该页面最近的交付 tag 与对应的 `docs/handover/<tag名>.md` 文档。公共组件改动要列出全部受影响页面，不能只按改动文件归属判断。
2. **确认前保持历史不可变**：改动生效后先下发地址等待用户确认；这期间提交业务代码即可，禁止修改交接文档内容。
3. **确认后原地更新文档**：每个受影响页面在原有 `docs/handover/<tag名>.md` 上直接编辑覆盖——以当前代码为准只更新需要更新的部分（章节、功能用例、用户流程），不重写整个文档；**「3.2 用户流程」按最新功能清单逐条增补/更新：改动涉及的功能流程同步更新，未改动的流程保留不动**。**不在新增文档，原文件直接覆盖写入**。自检全 `[PASS]` 后**必须** `git add -A && git commit`（提交信息 `docs: 更新 <tag名> 交接文档`），再打一个新的 `deliver-*` tag 标记本次修订代码的版本——**有改动就有提交，文档更新不允许停留在未提交状态**。
4. **追加修订记录**：在原有文档「五、对话过程摘要」中追加一条修订记录，格式为 `交付修订：继承 <上一tag>；本次变更：<准确变更摘要>。`，按时间顺序排在已有摘要的最后。若没有可定位的上一版，写明"未找到可定位的上一版交付 tag"，再按首次交付流程处理。
5. **核对最新状态**：自检通过后，检查该页面最新的 `deliver-*` tag 对应变革文档已包含本次变更；旧 tag 保留为历史快照。向用户报告新 tag 名与已更新的文档路径。

## Tag 命名

格式：`deliver-<语义名>-<YYYYMMDD>-<两位序号>`

- **语义名由 AI 从本次交付内容中分析提炼**：用**中文**短语概括本次交付的页面/功能，要让人仅凭 tag 名就能看懂这次交付了什么（如 `用户管理页`、`仪表盘图表`、`登录页`）；禁止 `新页面`、`修改`、`更新` 这类无信息量的名字
- **后缀** = 当天日期 + 两位序号，用于区分同主题的多轮交付：日期取当天，序号从 `01` 开始；先用 `git tag -l 'deliver-*'` 查已有 tag 决定序号
- 示例：`deliver-用户管理页-20260807-01`、`deliver-仪表盘图表-20260807-02`
- 打 tag 逐页进行（写文档 → 自检 → 提交 → 打 tag，见「推荐执行顺序」），全部页面完成后统一 `git push` 提交与 tag（无远端则仅本地提交 + tag，向用户说明未推送）
- 语义名**只用中文加日期数字后缀**：不含空格、英文和特殊符号，保证 git 与文件名跨平台可用（git 原生支持 UTF-8 tag 名，交接文档文件名与 tag 同名，同样是中文）

## 多页面交付：按页面拆分（强制）

一次用户认可覆盖**多个页面**（新增或修改了多个主页面）时，**按页面拆分交付物：涉及的每个页面各生成一份交接文档、各打一个 tag**，禁止把多个页面合并进同一份文档。

- **拆分粒度是页面，不是功能**：同一页面内的多个功能不拆分——写进该页面文档「功能说明」的多个用例块；只有跨页面才拆成多份文档
- **每个页面一个 tag**：语义名用页面名（如 `deliver-用户管理页-20260817-01`、`deliver-仪表盘-20260817-02`），序号当天用 `git tag -l 'deliver-*'` 查重后连续取号；文档与各自的 tag 同名
- **每份文档独立完整（自包含）**：五个一级章节每份都写全、可单独移交；「对话过程摘要」只写与该页相关的原始需求与迭代轮次，允许跨文档少量重复
- **公共改动的归属**：布局、公共组件、全局样式等跨页面改动不单独出文档——写进每个受影响页面文档的「DOM 树与组件说明」与「Design & UX」；只改公共组件且无页面改动时，并入主要使用该组件的页面文档并在文中说明
- **逐页循环执行**：对每个页面执行「写文档 → 自检全 `[PASS]` → 提交（`docs: <tag名> 交接文档`）→ 打 tag」，全部页面完成后统一推送提交与 tag（见下方「推荐执行顺序」）

## 存量核对与补全：先查 git，缺了就补（生成前硬性）

写任何交接文档之前，先在 git 里核对「对应的文档是否已存在」，缺失的并入本次生成一并补全——不默认从零开始写，也不放任已交付页面没有文档。

- **核对命令（全部只读）**：`git tag -l 'deliver-*'` 列历史交付 tag；`git log --oneline --all -- docs/handover/` 查历史文档记录（防文档曾被删）；对照工作区 `docs/handover/` 现有文件
- **核对范围**：① 本次交付涉及的每个页面；② 历史 `deliver-*` tag 覆盖过、但只有旧合并文档（一份文档写多个页面）而没有专属文档的页面
- **判定标准**：某页面「有对应文档」= git 历史中存在过文件名/语义名指向该页面、且内容以该页面为唯一主体的交接文档（历史存在过即算，不要求仍在工作区）；旧合并文档对其中每个页面都**不算**专属文档
- **缺失的补全**：每个缺失页面按正常流程生成专属交接文档并打各自 tag（日期用当天、序号接续取号）；「对话过程摘要」从本会话记录与 `git log --oneline -- <该页面相关路径>` 还原历史，还原不出的信息向产品经理反问澄清，**不得编造**；补全页面较多时（如超过 3 个）先向用户报告清单与工作量，经确认再批量执行
- **已存在的文档用于后续修订**：若工作区已有该页面的交接文档（非首次交付），后续页面调整时直接就地更新原文件，不按页新建文档（细则见「已交付页面的后续修改」节）
- **tag 在、文档丢**：历史 tag 存在但 `docs/handover/` 里没有同名文件时，先用 `git show <提交>:docs/handover/<tag名>.md` 找回内容写回文件（禁止用 `git checkout` 类命令），找回不了才按补全流程重写
- 补全的文档与正常文档要求完全一致：模板五章节 + `validate-handover.mjs` 全 `[PASS]`；完成后逐页向用户报告（补了哪些页面、依据是 tag 历史还是会话记录）

## 交接文档

- 路径：`docs/handover/<tag名>.md`，**文件名必须与 tag 名完全一致**（如 tag 为 `deliver-用户管理页-20260817-01`，文档就是 `docs/handover/deliver-用户管理页-20260817-01.md`）；**一份文档只写一个页面**（使用说明、DOM 树、用户流程都围绕该页展开），多页面交付按页面拆成多份（见上节）
- 本 skill 的使用者是**产品经理**，生成网页 demo 的目的是给其他人演示/试用。交接文档的**新增页面**与**复刻 demo** 两种场景要求完全一致。交接文档内容**只写五部分**：
  1. **使用说明**——描述**使用者实际使用这个页面的操作逻辑**：在这个网页上可以做什么、按什么顺序点哪里、每一步会发生什么、最终能完成什么事，并配一张对应的**用户操作流程图**（用 Mermaid `flowchart` 描述从进入页面到完成目标的全过程与分支，让演示者照着流程就能讲、照着流程就能试；**Mermaid 生成按 `references/mermaid.md` 执行**）；**写使用说明前，凡是有不明确、含糊或缺失信息的地方（页面能做什么、操作路径、边界/异常、给谁用等），必须向产品经理反问澄清，得到明确结论后方可继续撰写**——不得自行假设或脑补页面行为，问清前不写这部分内容；
  2. **DOM 树与组件说明**——给出页面的 DOM 树结构（用缩进/树状列出页面各区块的嵌套层级），并在树上标注每个节点对应的**当前项目自身的组件**（即本项目 `src/components`、`src/pages` 下实际存在的组件，而非 antd 等组件库里的原子组件），以及它们由哪些**白名单原子组件**（antd / Ant Design Pro / Ant Design X 等清单内组件）组合而成；说明每个当前项目组件归属哪个区块、承担什么职责，让拿到 demo 的人一眼看懂页面由项目自身的哪些组件构成、各自怎么由原子组件拼出来。**粒度硬性要求（前端实现依据）**：交接文档同时是前端工程师的实现依据——目标是前端拿到「本文档 + 页面原型」即可还原页面、无需反读 demo 源码，因此 DOM 树必须细化到**字段/控件级**：页面按分组区块逐组展开；每个可交互控件（Input / Select / Switch / Button 等）单独成叶子；**每个叶子行必须带 `#` 用途注释**，写明字段名或按钮名、必填性、校验规则、options 枚举值、placeholder、关键 props（如 `valuePropName=checked`、`type=primary`、`htmlType=submit`）；树后紧接着写「布局与样式要点」小节（内容区宽度与居中、栅格分栏、间距、响应式断点、禁用/loading 策略、关键色值）；有取数的页面在业务规则或 DOM 树节给出与 `mock/<domain>.json` 一致的接口契约示例（响应 JSON）；
  3. **设计与用户体验（Design & UX）**——交代本页面的设计依据与全局状态表现，让拿到 demo 的人明白这套页面为什么这么设计、各状态怎么呈现。必须包含：
     - **设计原则 / UX 原则**：列出指导本页面的设计原则（如「操作路径最短」「关键操作可撤销」「状态反馈明确」），有公司/团队 Design System 时给出链接
     - **用户流程（User Flow）**：**每个功能一条用户流程**，与本页「四、功能说明」的用例一一对应（功能名称与用例编号一致）；每条流程用文字或 Mermaid 描述「开始 → 步骤 → 决策点 → 结束」，并列关键分支路径与异常/退出路径（Mermaid 生成按 `references/mermaid.md` 执行）；可先加一条「总体流程」串起所有功能，再按功能逐一展开。**页面功能更新或新增后，同步增补/更新对应功能流程，不允许只保留一条旧流程**
     - **原型与设计稿**：交互原型（Figma/Axure 等）与视觉设计稿（UI）链接，并用表格列出关键页面清单（页面名称 / 说明 / 设计稿链接或截图）
     - **关键交互说明**：导航方式、手势/操作约定（移动端点击/长按/滑动）、动画与反馈要求（如需）
     - **全局状态与边界处理**：用表格列出各状态类型（加载中 / 空状态 / 错误状态 / 无权限 / 网络异常等）的**表现要求**（如加载中显示 Skeleton / 转圈 / 按钮 loading 态，空状态给文案 + 引导操作按钮，错误状态给明确错误原因 + 重试/返回入口等）
  4. **功能说明（按功能逐条写）**——对页面里的每个功能，**当作一个用例**来写，让拿到 demo 的人照着就能理解每个功能的目标、操作与校验规则。每个功能按下面的用例结构逐项说明（沿用 `use-cases.md` 的用例方法论，此处已并入模板）：
     0. **用例概述**（用表格或字段列出）：用例名称、用例编号（统一前缀如 `UC-LOGIN-01`，按模块分组）、参与者（游客/已登录用户/管理员等）、优先级（P0/P1/P2，P0 为核心）、前置条件（用例开始前必须满足的状态）、后置条件（成功结束后系统达到的状态）、触发事件（用户或系统触发本用例的动作）
     1. **功能目标**：用户能完成什么、解决什么问题（对应用例概述的「用例名称」）
     2. **用户场景 / 用户故事**：作为 [角色]，我希望 [动作]，以便 [价值]（对应「参与者」）
     3. **页面/界面说明**：入口（从哪里进入）、布局说明（顶部 / 主体 / 底部操作区，可配截图或原型链接）
     4. **正常流程（交互与操作流程）**：按步骤列出「点 X → 弹出/跳转 → 填写 → 提交 → …」，每步动作 + 系统反馈，按用户真实操作顺序（聚焦 → 输入 → 校验 → 提交 → 结果）
     5. **业务规则（字段规则）**：用表格列出每个字段（字段名 / 类型 / 是否必填 / 校验规则 / 默认值 / 错误提示文案 / 备注），并把可测试的硬性规则（敏感词脱敏、防重复发布、防暴力破解、长度/格式限制等）一并列出；涉及产品决策但未确认的（如失败锁定策略）如实标注「需产品确认」，不擅自假定
     6. **各种状态表现**：正常态 / 加载态（按钮 loading、不可重复点击）/ 成功态（Toast「操作成功」+ 刷新或跳转）/ 失败态（提示原因 + 保留已填内容）/ 空态 / 权限不足
     7. **异常流程（异常与边界场景）**：表格化列出每条异常（编号 / 触发操作 / 系统表现 / 处理结果），穷举输入校验、格式校验、长度限制、网络异常、重复提交、权限不足等场景；编号与正常流程区分（如 A1–A9 / B1–B7）
     8. **验收标准（可测试）**：用 `[ ]` 勾选项列出可测的验收标准（如「用户按主流程可顺利完成操作」「所有错误提示文案正确且位置合理」「加载/空/错误状态均有明确反馈」「移动端与桌面端表现符合设计稿」）
     > 写作参考：完整示例见 `use-cases.md` 的登录/评论用例，以及本目录下的 `handover.example.md`。**正常流程分步编号、异常流程表格化、业务规则可测试**是三条硬性要求。
  5. **对话过程摘要**——按时间顺序概括产品经理的原始需求、迭代中的每轮反馈与修改（改了什么、为什么改），直到确认满意，**放在文档最后**；
  除此之外不写交付概述、最终状态、如何继续等其他内容
- **写作参考**：拿不准格式时，照本目录下的 `handover.example.md` 示例写——尤其 **DOM 树部分，树的每一棵子树必须终止于白名单原子组件**（antd / @ant-design/pro-components / @ant-design/x / @ant-design/icons 等清单内组件），项目自身组件（`src/components`、`src/pages` 下的组件）只负责组合这些原子组件、承载业务逻辑，**不能成为 DOM 树的叶子**；在 DOM 树上把每个当前项目组件标注出来，并说明它由哪些白名单原子组件拼成，让拿到 demo 的人一眼看懂；**叶子必须细化到字段/控件级并带 `#` 用途注释，树后跟「布局与样式要点」小节**（参考示例中 `antd:Form.Item` / `antd:Table.Column` 的字段级写法）
- **生成骨架**：以 `references/handover.template.md` 为固定模板，**逐字照抄其五个一级章节与每个功能的 0–8 用例字段结构**，只把占位符替换为本次交付的实际内容；不得自行增删章节、改名或打乱顺序
- **生成后自检（硬性）**：文档写完、提交前，必须运行 `node scripts/validate-handover.mjs docs/handover/<tag名>.md`，脚本会校验五个一级章节唯一性、是否存在 mermaid 且含 flowchart、Design & UX 是否有独立用户流程且**每条功能都对应一条用户流程（3.2 流程数量与功能数量一致）**、每个功能是否含完整用例字段、异常流程是否为表格、DOM 树代码块是否恰好一个（防多个页面塞进一份文档）、DOM 树叶子是否为白名单组件、DOM 树叶子是否带用途注释（`#` 或括注，防粗粒度树）、是否残留 TODO/待补充/无依据假设、文件名是否与 tag 一致；**出现任一 `[FAIL]` 必须修正后重新运行直到全部 `[PASS]`**，校验不通过不得向用户报告完成
- **校验脚本必须在项目内可运行**：初始化后的项目 `scripts/` 下自带 `validate-handover.mjs`（由模板复制）；老项目缺失该脚本时，先从本 skill 的 `scripts/validate-handover.mjs`（或 `assets/project-template/scripts/`）复制进项目 `scripts/` 再运行，**禁止以"脚本不存在"为由退化为手工检查**
- 每份文档自检全 `[PASS]` 后立即提交并打对应 tag：`git add -A && git commit`（提交信息 `docs: <tag名> 交接文档`）→ `git tag <tag名>`，再处理下一页；全部页面完成后统一 `git push`（提交与 tag 一起推；无远端则仅本地提交 + tag 并向用户说明未推送）。**推荐顺序：写文档 → 自检 → 提交 → 打 tag →（全部完成后）统一推送**——若 tag 已先于文档提交打上，需删除本地和远端 tag 后重打（`git tag -d <tag>` + `git push origin :refs/tags/<tag>`）

## 推荐执行顺序

1. 用户确认满意
2. 业务改动的提交与推送（若还没提交）
3. 读取 `references/handover.template.md`、`references/handover.md`、`references/mermaid.md`
4. **多页面交付先拆分**：列出本次交付涉及的页面清单，为每页确定 tag 名（一页一个 tag，序号当天连续取号）；单页面交付只有一项，同一流程
5. **存量核对与补全**：按「存量核对与补全」节用 git 核对，把缺专属文档的页面（本次交付页面 + 历史合并文档覆盖的页面）并入第 4 步的清单，同样一页一 tag 一文档
6. **逐页循环**（每页一份文档，含补全页面）：
   1. 判断是否已有该页面的交接文档——已有则就地编辑覆盖原文件，没有则按模板新建；只写该页面（公共改动按归属规则写入；补全页面的对话摘要从会话记录与 git log 还原）
   2. 运行自检 `node scripts/validate-handover.mjs docs/handover/<tag名>.md`，按 `[FAIL]` 修正直至全部 `[PASS]`
   3. `git add -A && git commit`，提交信息 `docs: <tag名> 交接文档`（修订场景可用 `docs: 更新 <tag名> 交接文档`）
   4. `git tag <tag名>`，进入下一个页面
7. 全部页面完成后统一推送：`git push` + 逐个 `git push origin <tag名>`（无远端则仅本地提交 + tag 并向用户说明未推送）
8. 告知用户：**逐页列出**每页的 tag 名与交接文档路径（含本次补全的历史页面及其依据）
